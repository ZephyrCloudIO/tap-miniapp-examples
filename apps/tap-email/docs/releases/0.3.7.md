# TAP Email 0.3.7

This release addresses the history, meaning-search and Chloe setup gaps observed after publishing 0.3.6. It retains SDK **0.19.0** and minimum TAP host **2.24.1**.

## Changed behavior

- **History recovery:** a failed local history traversal retries from its committed cursor on refresh; simultaneous callers share one traversal and a completed traversal stays complete for that mounted session. Coordinator refresh/cron recover orphaned provider continuations from the saved page and generation. Recent-mail updates preserve `backfilling` coverage; stale continuation deliveries cannot rewind the saved page. A zero/invalid historical date is shown as unverified, and Settings shows unresolved failures.
- **Meaning search:** queries use the index already available rather than waiting for every local page to be embedded. An open Email surface maintains a private SQLite change queue in batches of eight threads, alongside mail updates and deletion tombstones. Unchanged saves do not requeue work. Queue acknowledgments are fenced against newer edits and model changes and persisted only after vectors flush; failed or cancelled work remains retryable. Model changes reseed the queue. Progress, pending updates, failure and retry are visible. Query/account/view changes cancel stale result publication.
- **Chloe setup:** token creation, host credential binding and specialist access are separate visible steps, with a route to installed Email settings. Successful authenticated read operations record verification against the current token hash; replacement resets it, and failed/expired/revoked credentials cannot establish it. Refreshing verification reports an actual tool read, without claiming which specialist performed it. Setup instructions remain visible after reopening.
- **Release identity:** package, manifest, specialist and packaged email-operations skill advance to **0.3.7**.

## Limits

These changes implement parts of **EP03, EP05 and EP11**, not those entire roadmap cards. Historical traversal primarily fetches metadata; the semantic input is available local subject/participants/snippet and stored plaintext previews, bounded to 24 KiB per thread. Complete body/attachment coverage, long-thread chunking, prefiltered recall beyond the existing top-100 candidates, avoiding re-embedding on label/read changes, and cleanup of older model collections remain separate work. No retrieval-quality or large-mailbox latency benchmark is claimed.

Local index maintenance runs while Email is open and resumes on reopening. It requires an installed local embedding model and granted private vector storage. A caught-up queue means observed local changes have been processed, not that provider history or every message body is complete. Existing wipe receipts continue to report incomplete removal of separately owned vector/audit storage; tombstones clean the active vector collection when maintenance runs.

SDK 0.19 cannot save an MCP secret or grant Chloe access. Those steps still use TAP settings. A token's successful-read receipt establishes usable credentials for that endpoint; it cannot attest to Chloe's identity or prove a complete search/read workflow through the installed host.

## Validation

Regression tests cover interrupted cursor recovery, duplicate history callers, orphaned provider jobs, partial-sync coverage, stale continuation delivery, zero-date coverage, bounded/restarted indexing, late acknowledgment versus newer edits, deletion/device-wipe tombstones, unchanged saves, model changes, cancellation, query execution during pending embedding, flush-failure retry, and token verification/rotation.

Verified locally: **511 Email tests** and **204 coordinator tests** passed. Additional passing checks: Email/TAP/coordinator typechecks, SDK manifest validation, repository static Test Lab validation, preview/desktop/QuickJS package assembly, package/MCP/activity ABI and React/source-map checks, production-origin guard, coordinator generated types, production deployment dry run and startup analysis. These checks do not prove live installed-host behavior.

## Rollout and acceptance

Apply coordinator migration **0019_mcp_connection_verification.sql** before deploying its new worker. The existing production deployment workflow applies D1 migrations before Worker deployment. Prefer completing that deployment before publishing/installing Email 0.3.7; the new client accepts older status responses as unverified.

After merge and publication:

1. Open the installed package and confirm each account's history state/horizon/failure count; interrupt and refresh a traversal, then verify it advances without restarting or losing current mail.
2. Observe meaning-index counts while issuing queries before catch-up. Reopen Email and confirm pending work resumes; change accounts mid-query and verify scoped results. Confirm a removed thread no longer appears.
3. Create a read token in Email Settings, save it in the installed MCP connection, enable the intended Chloe tools/skill, and ask Chloe to list accounts and read an exact message. Refresh verification, then replace the token and confirm verification resets. Never paste a token into chat or diagnostics.

This PR prepares 0.3.7. It does not publish it, grant credentials, or claim these live acceptance steps have passed.
