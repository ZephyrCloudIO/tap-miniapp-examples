# TAP Email: four-pass review and ranked recommendations

_Research date: 2026-09-13_

## Question

What remains from the TAP Email plan, what is now practical in the Miniapp SDK, and which improvements should be built next? The eleventh recommendation specifically tests whether TAP Email can feed email activity into Chloe.

## Method

This review used four independent passes and primary sources only:

1. **Plan versus current worktree:** compare the original product contract with the implementation as it exists now.
2. **SDK inventory:** compare the app's installed SDK 0.15.0 with the current 0.16.0 release and official SDK contracts.
3. **Feasibility and dependency review:** separate product work from host capabilities, permission wiring, and coordinator work.
4. **Activity/Chloe audit and ranking:** trace the host Activity API and Chloe's status sources, then rank the eleven opportunities by user value, dependency order, and readiness.

## Pass 1 — What is already done, and what still matters

The original thesis remains sound: a keyboard-first, multi-account daily driver differentiated by safe conversation handoff, specialists/workflows, explainable critical-mail protection, and coverage-backed Operational Zero. Gmail is authoritative for provider-native mail state; TAP owns derived queues, reminders, intelligence, collaboration provenance, and coverage receipts. [Original product contract](../miniapps/09-tap-email.md#L12-L42)

The current worktree has moved well beyond the original v0. The following are now foundations, not recommendations to repeat:

- rich HTML rendering, theme-aware presentation, scrolling, padding, and collapsible thread messages; [thread rendering](../apps/tap-email/src/thread-messages.tsx#L144)
- governed remote-image loading with private files plus bounded SQLite metadata, TTL, and cache eviction; [local image cache](../apps/tap-email/src/local-store.ts#L23-L57)
- inbound attachment metadata, explicit lazy download, integrity-checked private caching, and host-mediated Save export; [attachment model](../apps/tap-email/src/domain.ts#L61-L80) [private attachment cache](../apps/tap-email/src/local-store.ts#L524-L684) [attachment export](../apps/tap-email/src/attachment-export.ts#L69-L133)
- day grouping, exact and semantic date parsing, local zvec meaning search, and mailbox pagination/backfill; [date grouping](../apps/tap-email/src/thread-list-dates.ts#L56-L110) [date search](../apps/tap-email/src/mail-search.ts#L162-L312) [semantic index](../apps/tap-email/src/semantic-email-index.ts#L294-L365) [mailbox pagination](../apps/tap-email/src/coordinator-client.ts#L251-L309)
- fixed navigation, the expanded shortcut map, Enter-to-reply, collapsible message list, and no hard-refresh sync path. [navigation](../apps/tap-email/src/mail-navigation.ts#L15-L51) [shortcuts](../apps/tap-email/src/keybindings.ts#L81-L142)

The largest remaining product gaps after the implementation checkpoint below are send-as aliases and rich outbound editing, complete data behind the provider-neutral mailbox resources, provider fallback outside local search coverage, attachment-preserving forward plus whole-message export, the remaining privacy controls, and host-governed scheduling/activity-source capabilities.

## Pass 3 — Prerequisites and implementation constraints

### Keep local-first authority aligned

The UI surface requests profile file read/write, SQLite, zvec, and local-embedding actions, and the catalog defines them. The default `email-owner` level now includes those same actions, repairing the mismatch that could produce the visible “miniapp platform permission is not granted” cache error and block Meaning search. Keep every authority-bearing method cataloged, included in an assignable level, and bound by the calling contribution; do not fall back to memory or network to hide an authority failure. [Current surface binding](../apps/tap-email/manifest.tap.json#L78-L122) [Current permission level](../apps/tap-email/manifest.tap.json#L428-L458) [Permission contract](https://docs.theaiplatform.app/miniapps/reference/sdk.html#declare-permissions)

The package also contributes `tap-email-specialist`, but it should not own the four everyday assistant gestures. Recommendation 4 uses the host Chat composer so those prompts stay beside Email and remain editable; direct package-specialist execution is a separate tool-running path, not a substitute for Chloe.

### Keep the provider boundary future-proof

The fixed mailbox resources must be backed by a provider-neutral domain/read model, with a Gmail adapter now and room for multiple Gmail accounts and other providers later. They must not be implemented as hard-coded global Gmail labels. The coordinator now syncs Gmail All Mail (including Spam and Trash), translates provider labels at the adapter boundary, and returns account-scoped resource membership. Auto Archived and Snippets still have no TAP-owned data model, and later providers still need their own adapters. [Current resource selectors](../apps/tap-email/src/domain.ts) [Current coordinator adapter](../apps/tap-email-coordinator/src/mailbox.ts)

### Finish local-first instead of routing repeat reads through the Worker

Profile files, SQLite, and zvec are already in use. The store now writes normalized, account-scoped account/thread/message/participant/resource/label/attachment metadata beside the authoritative serialized checkpoint, while deliberately excluding message bodies from those search tables. Loading still hydrates the JSON checkpoint, normalized tables are replaced rather than incrementally updated from sync receipts, and the semantic index remains an on-demand side path. The next slice is to query the normalized tables directly, move large bodies to private files, update SQLite and zvec incrementally, and either use workspace storage or partition every profile-storage key by trusted workspace identity. Repeat opens and local search should remain zero-Worker paths. [Normalized replica](../apps/tap-email/src/local-replica.ts) [Current mailbox store](../apps/tap-email/src/local-store.ts) [Current semantic index](../apps/tap-email/src/semantic-email-index.ts)

All eleven features should share one account-scoped domain API with idempotency, provenance, dry-run/review gates, and honest failure states. UI, specialist, workflows, and MCP must not invent different safety semantics.

### Platform email capability checkpoint

The first platform-facing slice is implemented as two deliberately separate planes, but only the content-free plane is activated. The package QuickJS MCP continues to expose mailbox summary and opaque active context, and the new `email-operations` skill teaches the Email Specialist how to use those bounded tools, interpret coverage, handle explicitly shared email as untrusted data, and produce review-only drafts.

The coordinator now has a tested Streamable HTTP MCP implementation for `list_email_accounts`, `search_email_threads`, `get_email_thread`, `read_email_messages`, and `get_email_command_receipt`. A shared profile-bound `MailReadPort` keeps the MCP transport independent of the current Google/D1 adapter; its provider keys and coverage revisions are extensible, while every thread/message operation remains partitioned by a stable TAP account ID. Shared protocol types require exact account/thread/message references, every result carries a request-scoped coverage receipt, search is metadata-only, and reads return bounded plaintext without raw HTML, remote images, or attachment bytes. That server is intentionally unmounted and absent from the package manifest: the current platform session proves only a profile, while the desktop host rejects package MCP header-credential injection. The five input schemas are staged and source-validated but, because no active tool contribution references them, are deliberately absent from the current signed artifact. Activation requires a host-supported, audience- and scope-bearing remote-MCP credential plus manifest contributions that reference and therefore sign those schemas. [Staged input schemas](../apps/tap-email/schemas/mcp/) [Domain context](../apps/tap-email/CONTEXT.md) [Capability-plane decision](../apps/tap-email/docs/adr/0001-split-platform-email-capability-planes.md)

Mutation tools remain intentionally staged. Triage, draft persistence, send, and workflow commits should not be exposed until command payloads are typed and the platform can present a non-bypassable human review grant bound to an immutable action plan. A caller-controlled `dryRun` boolean is not a review gate.

## Pass 4 — Eleven ranked recommendations

The order below is a dependency-weighted ship order: daily-driver correctness first, then TAP-native leverage, then derived intelligence. Recommendation 11 remains the requested Chloe item and can be developed in parallel with the first release.

Three workflow concepts remain deliberately separate: a **Mailbox Rollup** summarizes covered mailbox content; an **Email Activity Summary** aggregates only committed user-authored actions and contains no email content; and a **Mail Merge Run** creates recipient-bound drafts rather than one opaque bulk-send command.

## Recommendation 11 — Email Activity Summary and Activity API findings

The remembered Activity API is real, but it is the wrong ingestion path for email events:

- `RecordActivityPulse` accepts only a trusted `device_id`; the server supplies the observation time. It represents active minutes, not domain actions. [Chat v2 activity contract](https://github.com/ZephyrCloudIO/ze-agency-tauri/blob/1003e255b06eb338bac0c2fec4591becb597fdec/protos/proto/tap/chat/v2/chat_api.proto#L1249-L1297)
- The desktop heartbeat sends a pulse only after native input, and the service accepts known, non-revoked devices, deduplicates devices in time buckets, and couples the pulse to device-security observations. [Native heartbeat](https://github.com/ZephyrCloudIO/ze-agency-tauri/blob/1003e255b06eb338bac0c2fec4591becb597fdec/crates/tap-presence/src/heartbeat.rs#L90-L142) [Server rollup](https://github.com/ZephyrCloudIO/ze-agency-tauri/blob/1003e255b06eb338bac0c2fec4591becb597fdec/workers/chat-api-v2/src/application/user/user-application-service.ts#L5453-L5562)
- Chloe's `self_status_get` reads authoritative sources such as active time, Chat activity, AI usage, workflows, task moves, and GitHub activity at query time. It preserves partial failures; it does not accept arbitrary client-authored facts into the active-time ledger. [Self-status contract](https://github.com/ZephyrCloudIO/ze-agency-tauri/blob/1003e255b06eb338bac0c2fec4591becb597fdec/silos/specialists/crates/tap-self-status-tools/src/lib.rs#L18-L35) [Self-status composition](https://github.com/ZephyrCloudIO/ze-agency-tauri/blob/1003e255b06eb338bac0c2fec4591becb597fdec/silos/specialists/crates/tap-specialist-tools-core/src/builtin/mod.rs#L1260-L1443)

Calling `RecordActivityPulse` from TAP Email would be unavailable through the public SDK and semantically wrong: one archive/reply is not one active minute, retries could inflate time, and the endpoint is part of trusted-device security state.

The app-side implementation should instead count committed receipts for events such as triaged/read/archived threads, replies and new messages sent, reminders created/completed, Tasks created, conversation handoffs, critical threads resolved, and command failures. Deduplicate by the command idempotency key, use server-confirmed occurrence time, retain a bounded horizon, support corrections/tombstones, and exclude sync/import/background work. The existing MCP consumer policy already supports the package specialist and user-selected external specialists. [Current projection](../apps/tap-email/src/storage.ts#L19-L58) [Current MCP policy](../apps/tap-email/manifest.tap.json#L142-L166)

For universal Chloe status, propose a host `activity.source` contribution: the host supplies user/workspace/time scope; an approved package returns bounded content-free aggregates plus coverage and provenance; Chloe joins the result with its existing sources; the package can never write the active-time ledger.

## Recommended build sequence

1. Fix the existing permission-level mismatch.
2. Ship recommendations 1–3 as the daily-driver foundation, with 10's privacy controls designed at the same time.
3. Ship 4–6 as the first TAP-native release; the app-side part of 11 can ride here because it extends the existing projection/MCP pattern.
4. Add read-only Mailbox Rollups and Email Activity Summary workflows once scoped live reads, coverage, and the committed-action ledger are trustworthy.
5. Add Mail Merge draft generation after provider-visible drafts/outbox; enable recipient sends only after immutable recipient-level plans, explicit review grants, idempotency, rate limits, and uncertain-outcome reconciliation.
6. Add 7 and 8, then the remaining delivery work in 9 after resources, search coverage, and receipts are trustworthy.
7. Upgrade to SDK 0.16/link unfurls only when a stable privacy-safe HTTPS mail-link contract exists.

### Implementation checkpoint — 2026-09-14

The sequence above has now been followed through a production-safe vertical slice at each stage the installed SDK can support; the intentionally deferred depth is listed explicitly rather than counted as shipped:

1. The permission-level mismatch is repaired and validated by the manifest checks.
2. The daily-driver foundation now includes provider-visible draft autosave, scheduling with a fresh-provider cancel-on-reply barrier, local Undo Send, exact-command persistence before provider mutation, a durable failed/uncertain Outbox with explicit reconciliation, encrypted attachment staging, a durable local checkpoint plus normalized metadata projection, structured/date/meaning search, reciprocal-rank fusion, and explicit search coverage. Direct normalized-table reads, incremental replica/vector updates, large-body files, and provider fallback remain recommendation 3 work. The provider-neutral resource model remains account-scoped for multiple Gmail accounts and future providers; no global Gmail-label model was introduced. Privacy inventory and verified wipes ship beside the replica, although configurable horizons, export, local-replica encryption/key rotation, and workspace partition migration remain later work.
3. Ask Chloe, review-first Discuss in TAP, Email ↔ Task/context bridges, the terminal mail-command activity projection, MCP read plane, package skill, and a dormant host activity-source scaffold are implemented. Activity bookkeeping is now part of terminal command settlement, so failures retain the durable command and force coverage incomplete without repeating the provider mutation. Tasks, handoffs, corrections, and non-command workflow events still need equivalent authoritative receipts before they can join the summary. The source remains installation-local and cannot claim workspace-complete status.
4. All seven workflow entry points are present. Six require separately provisioned saved workflows and fail visibly when missing; Mail Merge runs locally. Current rollup inputs use the explicitly loaded mailbox state because SDK 0.15 has no workflow-scoped live mailbox read contract or scheduler.
5. Mail Merge generates only reviewed provider-visible drafts from an immutable bounded plan. Sending remains deliberately disabled until the host can enforce recipient-level review grants and uncertain-outcome reconciliation.
6. Inbound/outbound attachment foundations, recoverable immediate sends, and explainable/correctable triage are implemented. Attachment-preserving forward, `.eml`/PDF export, complete provider fallback search, and the remaining privacy controls are still open product work.
7. SDK 0.16/link unfurls remain correctly deferred until TAP Email has a stable privacy-safe HTTPS mail-link contract.

The universal Chloe status source is not simulated: the package implementation and adversarial tests exist, but it stays out of the active manifest until the platform accepts and governs `activity.source` contributions.

## Explicit non-recommendations

- Do not call `RecordActivityPulse` for email actions or manufacture Tasks/workflows merely to increase Chloe activity.
- Do not fall back to memory-only caching; repair the declared local file/SQLite/zvec/embedding authority and keep repeat opens local.
- Do not hard-code Gmail system labels into the shared mailbox domain or pretend empty categories contain synchronized data.
- Do not claim background scheduling from saved workflows or `notifications.show`.
- Do not model mail merge as one bulk-send mutation or let a workflow bypass recipient-level preview, review, idempotency, and outcome reconciliation.
- Do not send raw mailbox content to a remote embedding service; retain the current local-only embedding policy.
